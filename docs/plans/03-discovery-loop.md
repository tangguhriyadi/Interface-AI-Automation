# Plan: `/automation` discovery loop

**Source**: conversational request (no PRD)
**Selected scope**: the LLM-driven observe → decide → act discovery loop in `/automation`, emitting a `CapabilityArtifactSchema`-valid artifact from a live target-app run, using the existing surface adapter and schema unchanged in spirit (extended where a real gap requires it). Structured JSONL run evidence + failure screenshots, for both discovery and replay runs. The escalation *handoff* mechanism (a human taking control of the live session) and the CLI are separate, later plans.
**Complexity**: Large

## Summary

Build the piece CLAUDE.md's discovery-loop section describes: each turn, snapshot the accessibility tree, assign per-frame refs, send a compact redacted view to the model; the model answers only through six structured tools (`click`, `type`, `select`, `read`, `done`, `escalate`) — never free navigation, never a selector, never a literal value; the system resolves the model's chosen ref into a locator chain and records it. Every action passes a policy gate before it executes, and an irreversible step is never executed during discovery. The run ends in exactly one of five distinct, recorded results: goal done, max steps, timeout, dead end, escalation. A successful run emits a capability artifact in the existing schema (extended with two new fields — see design decisions 8 and 9), then structured JSONL evidence plus a failure screenshot is written for the run, using the same mechanism replay gains too.

Validated by discovering the same goal the hand-authored `lookup_member_savings_balance` capability solves — login, search, read `memberName` + `savingsBalance` — live against target-app, then feeding the *discovered* artifact straight into the existing, unmodified `replay()` and confirming it succeeds. That round-trip is the strongest available proof the two systems agree on one artifact format.

## Design decisions

1. **`resolveRef` must learn to build a structural (row-header) locator, not just role+name — and the trigger is narrower and different than "no accessible name."** Live re-verification against the running target-app (2026-09-23, not assumed from source or from the earlier Phase-2 evidence-file comment that claimed otherwise) showed the balance/name value cells *do* carry an accessible name — it's exactly the rendered value (`"$1,234.56"`), computed from content, not a stable identifier. A role+name locator built from it would only ever match this one observed value and break on any other record — a genuinely different failure mode than "no accessible name," and the reason structural resolution must win even when a name is technically present. Extended: `resolveRef` prefers a `StructuralLocatorSchema` locator (row header as the distinguishing signal) over role+name whenever the target sits directly inside a `row`-role node alongside a `rowheader`-role sibling — regardless of whether the target itself has a name — except when the target *is* the rowheader (its own label, e.g. "Savings," is a stable identifier and resolves via role+name as normal). A node with neither a name nor a rowheader sibling still throws. This is not a general structural-inference solver, just the one proven pattern, matching `evidence/accessibility-snapshot-spike/balance-panel.aria.yaml`'s row → [rowheader, cell] shape.

2. **Irreversible-control knowledge lives in the app profile**, as a new optional `irreversibleControls: { role, name, exact }[]` on `AppProfileSchema` — human-authored, app-wide, matching how outcomes/recoveries/sessionExpiry already work. The alternative — asking the model to self-classify reversibility per click — would hand a safety-critical judgment to the one actor this project otherwise never trusts with it. Before executing any `click`/`type`/`select`, the driver resolves the model's chosen ref and checks role+name against this list; a match is refused (never executed) and surfaced back to the model as a tool result, so it can `escalate` itself. **Consequence, stated plainly**: discovery can only ever produce all-`safe`-step capabilities. An irreversible capability can only be hand-authored and reviewed, never auto-discovered — which follows directly from "never execute an irreversible step during discovery."

3. **`type`/`select` tool arguments name a declared input (`inputName`), never carry free text.** The model picks the ref and picks *which* declared input to type; the driver fetches the literal value server-side and sends it to the browser. This makes "recorded as `fromInput`, never a literal" true by construction, not by post-hoc matching of typed text against known values, and structurally forecloses the model typing anything undeclared. `read`'s `outputName` is symmetric: it must name one of the goal's declared, not-yet-written outputs.

4. **`done` names a ref, not a checkpoint — the system derives the checkpoint from it.** A model-authored `successCheckpoint` would break the same rule locators already follow ("the model picks, the system builds") and could pick a condition that happens to be true now but is fragile or PII-bearing later. Instead `done`'s argument is `proof: { frameId: string; ref?: string }`:
   - `ref` omitted → the model is pointing at a **frame's presence** as the proof; the driver derives `{ kind: "frame_present", frame }`, with `frame` built from that `FrameSnapshot`'s `title`/`name`/`url` (in that preference order). Refused if `frameId` is `"main"` — the main frame is always present, so that's a vacuous, non-distinguishing checkpoint; the model is told to point at something more specific instead.
   - `ref` given and resolves to a `heading` node → derive `{ kind: "heading_starts_with", text, frame? }`. `text` is a **stable prefix**, not the literal full heading: if the heading contains `": "`, the prefix is everything up to and including the colon (the same shape the hand-authored artifact already uses — `"Member:"` from `"Member: Elena Cho"`); otherwise the full heading text is used as-is (no separator present to imply a variable PII-bearing suffix).
   - `ref` given and resolves to a non-heading text-bearing node (alert, paragraph) → derive `{ kind: "text_contains", text, frame? }` using the same stable-prefix rule; if no colon is present, the full text is used only after it clears the safety net below.
   - **Safety net, applied to every derivation regardless of path**: the derived `text` is checked against every `secret`/`pii`-sensitivity input literal and every `secret`/`pii`-sensitivity output value already read this run. Any match refuses the derivation outright with a clear reason (never silently truncated further) — the model has to point at a different, more stable ref instead.
   - Exactly as before: the derived checkpoint is then verified **true** against the current snapshot, and every declared output must already be written, before `done` is accepted. Either failure is a refusal, not a thrown error — the loop continues.

5. **Locator `rationale` stays 100% system-generated, from observed facts only — never model text.** `resolveRef`'s existing role+name rationale (`"Resolved from snapshot ref X in frame Y (ordinal N among role elements named Z)"`) is extended, not replaced, to also report *why* that strategy was chosen over the alternative: how many other elements in the frame share the same role+name (explaining whether/why `nth` was needed), and — for the structural branch — that role+name resolution was unavailable (no accessible name) before row-header structural resolution was used, phrased the same way the hand-authored artifact's own structural rationales already are. A discovered chain only ever contains the single strategy actually resolved (discovery never invents a brittle CSS/XPath fallback, since the model never writes selectors) — the generated rationale says so explicitly, as a note to the human reviewer that a fallback strategy may be worth adding by hand. If the model's own stated intent for a ref is captured anywhere (useful traceability, not required), it lands only in the evidence turn log as a distinctly-named `modelRationale` field — never merged into, or presented as, the artifact's own `rationale` string.

6. **`approvalState` makes "reviewable" real instead of asserted.** `CapabilityArtifactSchema` gains `approvalState: z.enum(["draft", "approved"]).default("draft")`. Discovery always emits `draft`; nothing in this plan reads or gates on this field yet (no unattended-replay gate is being built now) — it exists so that gate can be added later without another schema change. The existing hand-authored `lookup-member-savings-balance.artifact.json` is updated to `"approved"`, since a human (me, working with the user) actually reviewed it; re-validated and the full fast + live suites re-run to confirm the new field changes nothing about existing behavior.

7. **Shared policy module, not two allowlist implementations.** `isWithinAllowlist` (currently private to `executor/replay.ts`) moves to a new `executor/policy.ts`, imported by both `replay.ts` (unchanged behavior, just relocated) and the new discovery loop — CLAUDE.md requires the allowlist enforced during discovery *and* replay, and this project's own stated value is one implementation, not two that could drift.

8. **Evidence writing stays outside `replay()`/`discover()` themselves.** `replay()` is currently a pure function with zero filesystem I/O, proven by a unit suite that never touches disk. A new `evidence.ts` module is called explicitly, after the fact, by whatever drives a run — keeping both executors testable with `FakeAdapter`/`FakeModel` alone, no filesystem mocking required in their own test suites.

9. **No CLI yet — Phase 7's live validation calls `discover()` from a throwaway script**, the same pattern already used earlier this session to verify `memberName` live. The permanent invocation path is the CLI plan.

## Phases

### Phase 0 — Dependency & env
- **Action**: add `@anthropic-ai/sdk` to `automation/package.json`. Add `ANTHROPIC_API_KEY` (never logged) and `DISCOVERY_MODEL` (default `claude-sonnet-5`) to `.env.example`, same never-committed discipline as the existing target-app credentials.
- **Validate**: `npm install`, `npm run build` clean.

### Phase 1 — App profile, capability schema, and `resolveRef` extensions
- **Action**: `AppProfileSchema` gains `irreversibleControls: { role, name, exact }[]`, default `[]`. `CapabilityArtifactSchema` gains `approvalState`, default `"draft"`. `resolveRef` gains the row-header structural branch (design decision 1) and the richer, fact-based rationale on both branches (design decision 5). Update `lookup-member-savings-balance.artifact.json` to `"approvalState": "approved"`.
- **Validate**: new schema tests (valid/invalid `irreversibleControls`; `approvalState` defaults to `"draft"` when omitted, accepts `"approved"`, rejects any other string); `resolveRef` tests (nameless cell in a row with a row header resolves to a `StructuralLocatorSchema` locator matching the hand-authored shape; a nameless node with no row header still throws with a clear message; rationale strings assert on the new "why this strategy, what wasn't available" content). Re-run full fast suite (140 tests) and the live suite — confirm the schema additions change nothing about existing behavior.

### Phase 2 — Shared policy module
- **Action**: extract `isWithinAllowlist` into `executor/policy.ts`; `replay.ts` imports it instead of defining it. Add `isIrreversibleControl(profile, role, name)`.
- **Validate**: `replay.ts`'s existing allowlist test suite passes unchanged against the relocated function (proves the extraction is behavior-preserving); new tests for `isIrreversibleControl` (exact match, no match, empty list default).

### Phase 3 — Model seam
- **Action**: `DiscoveryModel` interface (`chooseNextAction(context): Promise<ModelTurn>`); `AnthropicModel` wrapping the SDK with the six tools (`click`, `type`, `select`, `read`, `done` with the `proof` shape from decision 4, `escalate`); `FakeModel` returning a scripted queue of turns for tests. Zod-validate every tool call's arguments before trusting them — invalid arguments become a tool-result error turn fed back to the model, never a thrown exception that kills the run.
- **Validate**: `FakeModel`-backed tests that a malformed tool call (bad ref, unknown `inputName`/`outputName`, malformed `proof`) produces an error turn and the loop can continue past it.

### Phase 4 — Compact snapshot view
- **Action**: `compactView.ts` filters each frame to interactive-or-readable nodes, includes role/name/value/row-header-hint and `frameId` per ref, and redacts any field whose current value was set by typing a `secret`-sensitivity declared input.
- **Validate**: tests against real captured snapshots (reusing the `evidence/accessibility-snapshot-spike/` fixtures already in the repo) — redaction holds for a secret-populated field, refs stay frame-scoped, a nameless row-header cell surfaces its row-header hint.
- **Correction after the first pass**: the wrapper-cell exclusion (any `cell` with children is dropped) was too broad — a cell wrapping exactly one leaf control (an "Actions column" link/button, one per row) is common in table-heavy legacy apps and was being dropped along with genuine structural wrappers, silently losing the only ref the model could act on. Narrowed to exclude a cell only when it nests another table/rowgroup/row/cell, or wraps more than one leaf control — a single-leaf-control cell stays included, and `findRowHeaderSiblingName` (adapter/snapshotParser.ts, shared with `resolveRef`) was extended to reach one level through such a wrapping cell so the row-header hint still lands on the control itself, not just the cell. Covered by new tests: one link per row (hint survives), two links in one cell (cell excluded, but each nested link still independently hinted).
- **A real finding, not just a limitation — cited for REPORT.md's Safety section**: checked live whether the snapshot parser captures anything that structurally distinguishes a password field from a plain textbox (asked when reviewing ref-based secret redaction, since ref-based marking depends on the loop's own bookkeeping surviving a re-render). It does not: a filled password field parses as plain `textbox "Password": secretpass` — Playwright's `ariaSnapshot()` shorthand carries no `type`, `protected`, or masking attribute for it, and the capture doesn't even mask the typed value itself. The only way to distinguish it would be reading the DOM `type` attribute directly, which would cross the accessibility-tree-only perception boundary this project holds everywhere else (the same boundary that makes the "swap one adapter for a desktop AX API" story in REPORT.md credible) — not worth breaking for this. Consequence: ref-based redaction (`CompactViewOptions.redactedRefs`) is necessary but provably not sufficient on its own, which motivated the second, independent layer below.
- **A second, independent redaction layer: value-based, not field-based.** `executor/redact.ts` gained `scrubSecretValues(text, secretValues)` — replaces every exact occurrence of any given literal secret value anywhere inside a string, not just in a field the caller expected it in. `compactView.ts`'s `redactSecretValuesInView(view, secretValues)` applies it across every string field (name, value, rowHeader, frame description) in every frame of a `CompactSnapshot`. This doesn't depend on the loop correctly remembering which ref a secret was typed into (ref-based marking's dependency, and the thing a page re-render could break), and it also catches a case neither mechanism anticipated: the app itself echoing a typed value back somewhere else — an error message, a URL — that ref-based marking was never told to redact. The discovery loop (Phase 5) applies both layers before any compact view reaches the model: ref-based first (redacts the field it knows about even if the value also appears verbatim elsewhere), then value-based as the net. Phase 6's evidence writer applies `scrubSecretValues` too, independently, to whatever it serializes — the same primitive, not a second implementation.

### Phase 5 — The loop (done)
- **Action**: `discover(goal, appProfile, adapter, model, options)` — turn cycle (timeout check → max-steps check → snapshot → dead-end check → compact view, ref-redacted then value-scrubbed → model turn → dispatch → record), `deriveCheckpoint.ts` (decision 4, including the PII/secret safety net), dead-end detection (`snapshotsStructurallyEqual` — role/name/text/attrs/children, ignoring `ref`/`ordinal` — across N consecutive unchanged iterations, default 3), max-steps and timeout options (defaults 25 / 120s), `DiscoveryResult` (`done | max_steps | timeout | dead_end | escalated`, each carrying a `turns: DiscoveryTurnLogEntry[]` audit trail; `done`'s capability always has `approvalState: "draft"`, `businessOutcomes: []`, and steps whose `classification` is always `"safe"` — a discovered capability can never contain an irreversible step, by construction).
- **Design refinement beyond the plan text — `done` re-verifies against a fresh, independent snapshot, not the one the proof was derived from.** Deriving a checkpoint's text from the same snapshot used to immediately verify it is tautological (the text is extracted from that exact snapshot, so it always starts-with/contains itself) — the "verify it's actually true" step as originally written had no real teeth. Fixed: after deriving the checkpoint, `discover()` calls `adapter.snapshot()` again and evaluates the derived checkpoint against *that* fresh snapshot before accepting — genuinely catching drift between the moment the model chose its proof and the moment the driver is about to trust it, in the same spirit as CLAUDE.md's "never assume a click worked" and the per-step-checkpoint addition earlier in `/automation`'s life. This is what makes the "checkpoint not yet true" refusal test constructible and meaningful rather than unreachable.
- **Malformed model turns are not fed back into the model's own conversation history**, only into the result's `turns` audit log — the model is forced to emit some tool call every turn (`tool_choice: "any"`, Phase 3), so a schema-invalid one is treated as a rare formatting slip rather than something worth reconstructing fake conversation state for. It still consumes a step (counts toward `max_steps`) and leaves the page unchanged (counts toward `dead_end`), so a model that only ever emits malformed calls is still bounded, just less "helped" to self-correct than a genuine refusal (which *is* fed back).
- **Validate**: 19 new tests (`test/discovery/deriveCheckpoint.test.ts`, `test/discovery/discover.test.ts`), all via `FakeModel` + `FakeAdapter`, no network, no browser: happy path to `done` (capability is `draft`, every step `safe`, `type` records `{fromInput}` never a literal); `done` refused for a missing declared output, then a retry succeeds; `done` refused when the fresh re-check contradicts the derived checkpoint, then a retry succeeds; an irreversible-control click refused (never reaching `adapter.click`), then the model escalates; each `deriveCheckpoint` branch (heading-with-colon, heading-without-colon, non-heading text, frame-only, and its `"main"`-frame refusal) plus the PII/secret safety-net refusal, at the `deriveCheckpoint` unit level; `dead_end` trigger; `max_steps` trigger (confirms the model is never called again once the budget is spent); `timeout` trigger (an already-exhausted budget stops before the first model call, no real-time waiting needed in the test). Full fast suite: 20 files, 243 tests, all passing; live suite re-confirmed unaffected (3/3 + 1 skipped).

### Post-Phase-5 fixes, before Phase 6 (done)
Three real problems, not gaps to note, found on review of the Phase 5 loop:

1. **Discovery ignored the app profile except for irreversible controls — no business-outcome, recovery, or session-expiry detection at all.** A recoverable interstitial appearing mid-run would have been visible in the compact view, and the model dismissing it itself would have been recorded as a permanent step — an artifact that only works when that interstitial happens to appear. Fixed by extracting `replay()`'s session-expiry/business-outcome/recovery detection (previously inline in its `checkTransition`) into a new shared `executor/appDetection.ts` (`createAppDetector`) — the same "one implementation, not two" rule `adapter/matchers.ts` and `executor/policy.ts` already follow. `replay()` was refactored to call it too, not just discovery, so there's genuinely one implementation: its full existing test suite (25 tests) and the live suite both still pass unchanged, confirming the extraction is behavior-preserving. `discover()`'s loop now calls the detector at the top of every iteration, before the compact view is built: a matched recovery is dismissed and re-snapshotted invisibly (never a step — proven by a test asserting the model's first compact view is already post-dismiss, and that a run reaching `done` has exactly the model's own steps, none extra); a matched business outcome or session-expiry signal ends the run immediately with its own distinct `DiscoveryResult` status (`business_outcome` / `session_expired`), rather than leaving the model to flail until `dead_end`. `businessOutcomeNames` passed to the detector is every outcome the app profile declares (`Object.keys(appProfile.outcomes)`) — unlike replay, discovery has no capability yet to narrow the list to. Recovery exhaustion or a failed dismiss action maps to `escalated` — a system-level problem the loop can't resolve itself, distinct from the model flailing.
2. **`knownValues` blocked every read value, secret and pii alike, from ever appearing in a checkpoint — including an incidentally generic one.** Blocking genuine PII (a name) from a checkpoint is correct; blocking a short, generic word a `pii`-sensitivity output happened to read back (a status like `"active"`) would have then refused *any* checkpoint containing that common word for the rest of the run, as an unintended side effect. Fixed: `MIN_SCRUB_PATTERN_LENGTH = 7` in `discover.ts` — a value must be at least 7 characters to be used as a scrub/block pattern (both compact-view redaction and the checkpoint safety net draw from the same filtered list). 7 excludes `"active"` (6) while still protecting a real name (`"Elena Cho"`, 9) or a real credential. Documented at the constant itself; tested both directions (a short value no longer blocks `done`, a long one still does).
3. **The timeout was only checked between iterations, so a hung model call would never terminate.** `discover()` now bounds each `model.chooseNextAction()` call to whatever remains of the overall `timeoutMs` budget (`withTimeout`, racing the call against a timer, computed fresh immediately before the call — recovery detection earlier in the same iteration can itself take time). A genuine model-call error still propagates normally; only an actual timeout is turned into `status: "timeout"`. Tested with a `DiscoveryModel` whose `chooseNextAction` deliberately never resolves — the run still completes (in milliseconds, not by waiting out a real timeout) with `status: "timeout"`.

**Validate**: 6 new tests in `test/discovery/discover.test.ts` (mid-run business outcome, mid-run session expiry, invisible recovery dismissal, short-value-not-blocked, long-value-still-blocked, hung-model-call bounded) plus `replay.test.ts`'s full existing suite re-run unchanged to prove the `appDetection.ts` extraction preserved replay's behavior exactly. Full fast suite: 20 files, 249 tests, all passing; live suite re-confirmed unaffected (3/3 + 1 skipped, including the 10003 interstitial-recovery scenario now flowing through the shared detector).

**The allowlist/hard-failure gap disclosed above was closed in the same sitting, not deferred**: discovery needs the allowlist even more than replay does — replay runs a fixed, human-reviewed artifact, but discovery is model-driven and can click any link on the page, so an off-allowlist navigation could otherwise get recorded straight into the artifact as a permanent step. `discover()`'s per-iteration checks now start with the same two checks `replay()`'s `checkTransition` runs first, using the exact same shared functions (`isWithinAllowlist` from `executor/policy.ts`; `adapter.lastNavigationStatus()`), each ending the run with its own distinct `DiscoveryResult` status: `allowlist_violation` (carries the offending `url`) and `http_error` (carries the `httpStatus`) — checked before any page content is read, same order as replay. Discovery has no tenant-overlay concept, so the allowlist origin is always the app profile's own `originPattern`, unlike replay's overlay-aware resolution. 2 new tests: an off-allowlist click stops discovery before the model is ever asked what to do next (so there was no chance for a step to be recorded off the back of it); a 5xx stops discovery before the first model call. Full fast suite: 20 files, 251 tests; live suite unaffected (3/3 + 1 skipped).

### Phase 6 — Evidence (done)
- **Action**: `screenshot(): Promise<Buffer>` added to `SurfaceAdapter`/`PlaywrightAdapter`/`FakeAdapter` (a real `page.screenshot()` PNG on the real adapter). `automation/evidence.ts`'s `writeReplayEvidence()` and `writeDiscoveryEvidence()` (two entry points, not one `writeRunEvidence()` — their result shapes and available context differ enough that a shared low-level file writer plus two thin, domain-specific wrappers reads more clearly than one function branching on `runKind`): `steps.jsonl` (one `StepRecord`/turn per line) plus a human-readable `summary.json`, written under `evidence/<discovery|replay>/<timestamp>[-<capabilityId>]/` — discovery has no stable id to name the folder by until it succeeds, so its directory is timestamp-only. A screenshot is captured only when the run didn't end in a clean success (`success`/`done`/`business_outcome` all skip it — a business outcome is a recognized answer, not a problem needing a picture). Both stay outside `replay()`/`discover()` themselves (design decision 5) — called explicitly, after a run completes, by whatever drives it.
- **Value-based scrubbing applied to everything written to evidence, not just the compact view.** Every free-text field (an `escalated`/`failed` result's `reason`/`observed`/`expected`, a discovery turn's `detail`, an `allowlist_violation`'s `url`) is passed through `scrubSecretValues` before being written, using the run's own known secret/pii values as the pattern list — `DiscoveryResult` gained a `knownSensitiveValues: readonly string[]` field for exactly this (every secret/pii value used this run, already length-filtered the same way the checkpoint safety net is); replay's evidence writer derives its own equivalent list from `capability.inputs`/`capability.outputs` + the literal `inputs` and `result.outputs` the caller already has, so `ReplayResult` needed no new field. The motivating case: the model's `escalate` reason is free text and may quote page content, including something like a member's name — nothing about its construction guarantees it won't. `StepRecord.attemptedValue`/`observedValue` and a `read` turn's `detail` are already redacted by declared sensitivity at construction (existing, sufficient primary defense) — the value-based pass over them is a deliberate no-op-in-practice second layer, not the mechanism actually protecting those fields.
- **A success/done result's raw values are redacted specifically for evidence, separately from the in-memory result.** `ReplayResult.success.outputs` stays deliberately unredacted for the caller ("that's what the caller asked for" — an existing, correct design decision) — but CLAUDE.md's safety rule ("never persist ... into artifacts, logs, or evidence") applies to the *persisted* copy regardless, so `writeReplayEvidence`'s summary redacts each output by its **declared** sensitivity, unconditionally (not length-gated like the scrub list — this is a known field with a known sensitivity, not free text where only a best-effort match is possible). Verified live: a real `replay()` success run's evidence summary shows both PII outputs as `"[REDACTED:pii]"` while `result.outputs` itself, inspected directly, still holds the real values.
- **The human-readable summary** carries exactly what was asked: goal/capability id, result status (+ status-specific detail), step/turn count, `durationMs` (new field on both `ReplayResultCommon` and `DiscoveryResultCommon` — neither exposed a total run duration before), which recoveries fired, and — for replay — each step's `matchedStrategy`, `action`, `outcome`, and `durationMs`. Confirmed live against the real `lookup_member_savings_balance` artifact: the summary correctly shows `structural` as the matched strategy for both row-header reads and `role` for everything else.
- **Validate**: 6 new tests in `test/evidence.test.ts` — hand-built `ReplayResult`/`DiscoveryResult` fixtures (not solely routed through real `replay()`/`discover()`, since neither currently constructs a scenario where a raw secret genuinely reaches a free-text field — the same reasoning that made `compactView.ts`'s original value-based-redaction test synthetic) directly prove: JSONL + summary redaction for a success run holds; the scrub layer catches a secret in a `failed` result's `observed` text; a screenshot is captured for `escalated`/non-`done`, not for `business_outcome`; a member name quoted in a discovery `escalate` reason is scrubbed from both the JSONL and the summary. Plus two live checks: a real `replay()` success run's evidence end to end (redacted summary/JSONL, no screenshot, `matchedStrategy` per step correct), and `PlaywrightAdapter.screenshot()` itself returns real, correctly-signed PNG bytes from the live browser. Full fast suite: 21 files, 257 tests, all passing; live suite re-confirmed unaffected (3/3 + 1 skipped).
- **Post-Phase-6 fixes, before Phase 7:**
  1. **`baseDir` was `process.cwd()`-relative, not repo-root-relative.** `/automation` is its own npm project and every command runs from inside it, so the documented "defaults to the repo-root convention" claim was false in practice — evidence would have landed in `automation/evidence/`. Fixed: the default (`REPO_ROOT_EVIDENCE_DIR`) is now derived from `evidence.ts`'s own module location (`import.meta.url`, one level up from `automation/`), not the process's working directory. 2 new tests `process.chdir()` to an unrelated temp directory before calling each writer with no `baseDir` override, proving the result still lands under the real repo-root `/evidence/`. Verified live too: ran `replay()` for real from inside `/automation` and confirmed both runs landed under `<repo-root>/evidence/replay/`, with no stray `automation/evidence/` created.
  2. **The summary didn't record which inputs a run was called with.** Two runs of the same capability with different inputs left nearly-identical evidence, with nothing to answer "what input produced this?" — the first debugging question a reviewer has. Both summaries now carry an `inputs` object: every declared input's name and sensitivity, value redacted per the existing rule (`redactForLog`) — a `none`-sensitivity input's literal value shows as-is (e.g. confirming which username a run used), a `secret`/`pii` input's value stays exactly as hidden as it already is everywhere else in evidence. Worth stating plainly: this does not make a `pii`-sensitivity input like `memberId` distinguishable by its literal digits in evidence — that's the redaction policy working as designed, not a shortfall of this fix; the two live `10001`/`99999` example folders from before this fix still won't show which memberId was used unless a capability declares that input's sensitivity as something other than `pii`.

Full fast suite: 21 files, 259 tests, all passing; live suite re-confirmed unaffected (3/3 + 1 skipped).

### Phase 7 — Live validation (round-trip + escalation done; a real evidence-redaction gap found and disclosed, not yet fixed)
- **Prerequisite**: `irreversibleControls` in `capabilities/fake-credit-union-console.app-profile.json` was empty — Phase 7 needs at least one real, live-verified irreversible control to prove the policy gate against. Added `{ role: "button", name: "Open Sub-Account", exact: true }`, live-verified on the member detail page (`evidence/app-profile-verification/irreversible-control-open-sub-account.aria.yaml`, findings.md addendum) — deliberately not clicked as part of verifying it, since only its existence and exact name needed confirming.
- **Action**: a throwaway script drove `discover()` against the running target-app (the user's own instance — never started/stopped/restarted by this work) for the same goal the hand-authored artifact solves — login, search, read `memberName` + `savingsBalance`, discovered live, not copied from the existing JSON.
- **Two real bugs found and fixed by the first live attempt** (which ended `dead_end` instead of `done`):
  1. **`dead_end` false-triggered on legitimate consecutive reads.** A successful `read` never changes the page by design — so reading two declared outputs in a row (an entirely ordinary shape for this goal) looked structurally identical to the model being stuck, and the no-op streak crossed the default threshold purely from real progress. Fixed: `discover()` now resets the streak when either the snapshot changed *or* a new output was written since the last check (`previousWrittenOutputsCount`), not just the first. New regression test: three consecutive successful reads on a never-changing page, ending in `done`, not `dead_end`.
  2. **The compact view's frame header was ambiguous and the model mis-parsed it.** `[frame iframe:Account Balance: title="Account Balance"]` gives no boundary between the frameId (which itself contains a colon) and the descriptive attribute that follows — confirmed live: the model copied the whole trailing string as if it were the frameId, and the resulting `read` was correctly refused, wasting a turn on a formatting bug, not a real mistake. Fixed: `frameId` is now its own quoted `frameId="..."` key, always first and unambiguous — `[frame frameId="iframe:Account Balance" title="Account Balance"]`.
- **Re-run after both fixes: full round-trip succeeded.** `discover()` reached `done` in 9 turns; the emitted artifact validated against `CapabilityArtifactSchema` with `approvalState: "draft"`; its structural locators independently rediscovered the same row-header pattern the hand-authored artifact uses (`rowHeader: "Name"` / `"Savings"`), with rationale strings correctly stating *why* (the cell's own name is the observed value, not a stable identifier). Feeding that discovered artifact straight into the existing, unmodified `replay()` against a fresh session succeeded, returning the real data (`memberName: "Elena Cho"`, `savingsBalance: "$1,234.56"`) for memberId `10001`.
- **Live proof of `escalated`**: a goal requiring the model to open a sub-account. It logged in, searched, attempted the irreversible click, was refused with the designed message ("...call escalate if this action is required"), and escalated with a clear, accurate reason — the policy gate, the refusal-as-nudge design, and the model's own judgment all worked exactly as intended.
- **A real gap this escalation run exposed — found, root-caused, and fixed by construction, not by filtering.** The model's escalate reason quoted the member's name — "...opening a new sub-account for member Elena Cho..." — verbatim, unredacted, in both `summary.json` and `steps.jsonl`. Root cause: `knownSensitiveValues` only accumulates values the driver *itself* caused to enter or leave the system (a typed input, an explicitly-read output). This goal declared zero outputs, so nothing was ever formally "read" — but the member's name is still visible to the model directly in the compact view (deliberately, by design: PII stays visible so the model can do its job) and the model was free to quote *any* visible page content in free text at any time, independent of whether a `read` tool call ever captured it. Filtering that free text after the fact would only ever be as complete as whatever the driver happened to know was sensitive — the same structural limit every value-based scrub layer in this project already has.

  **The actual fix removes the free-text channel entirely**, rather than trying to filter it. Every other tool already follows one rule — the model points, the system composes: it never writes a locator, never writes a checkpoint, never supplies a literal input value. `escalate`'s free-text `reason` was the one exception, and the exception is exactly what leaked. `EscalateArgsSchema` (`discovery/tools.ts`) now takes a closed `reasonCode` (`action_refused_irreversible | stuck | unexpected_state | cannot_complete`) plus an optional `frameId`+`ref` pointing at the element the model considers blocking — the same shape every other tool's target uses, and, like every other tool's target, never interpolated into human-readable text. `discover.ts`'s `composeEscalationReason()` builds the actual reason string entirely from facts the driver already holds and already redacts: the reason code, the turn count, the current URL, and the last tool call's own already-safe result text (every `TurnHistoryEntry.result` this loop constructs is already either a structural description — a ref, a role, a control name from the app profile or the page's own stable UI labels — or redacted by declared sensitivity; never raw page content). There is now no channel for the model to write prose into an escalation at all, so there is nothing to scrub and no over-redaction tradeoff to weigh — the exact three options considered and set aside earlier don't apply anymore, because the thing they were all trying to filter no longer exists.

  Re-ran the identical live escalation scenario after the fix: the model correctly chose `reasonCode: "action_refused_irreversible"`, the composed reason (`"reasonCode=action_refused_irreversible; afterTurns=6; url=...; lastAction=click; lastResult=\"refused: ...\""`) contains no member name or any other page content, confirmed by grepping the written evidence. The original leaked folder was deleted and replaced with this one. The finding stays documented here in full — including the exact leaked text — because it's a real thing that happened and is worth citing in REPORT.md's safety section, not because the leak itself is still present anywhere on disk.

- **Screenshots are a separate, deliberately unaddressed PII channel.** A screenshot captures whatever is on screen — member names included — so "never persist PII into evidence" cannot be made absolute while screenshots exist at all; no amount of text-level scrubbing touches image bytes. Not solved here, and not silently ignored either: recorded plainly as a known, deliberate tradeoff. Screenshots are captured only on failure/escalation (`needsScreenshot()`, `automation/evidence.ts`), never on a clean success — the narrowest scope this project's design already gives them — and a production deployment of this system would need its own access control and retention policy for the evidence directory specifically because of this channel. Left for REPORT.md's safety section to cover in full.
- **Validate**: the round-trip above; the live `escalated` proof above, re-run and re-verified clean after the reasonCode fix. `dead_end`/`max_steps`/`timeout` stay proven at the `FakeModel` unit level (Phase 5) — those are driver logic, not model behavior — though the dead-end fix above was itself found via a live run, not a unit test, since it required a real model choosing a real action sequence a hand-scripted `FakeModel` scenario hadn't happened to cover. New unit coverage for the `escalate` redesign: `tools.ts` rejects free text and a reasonCode outside the closed set, requires `frameId`/`ref` together or not at all; `discover.test.ts`'s three escalate scenarios updated to the new shape, asserting the composed reason contains the reason code and (when applicable) the prior action's already-safe result text, never anything the model wrote. Full fast suite: 21 files, 265 tests, all passing; live suite re-confirmed unaffected (3/3 + 1 skipped).

## Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| Model doesn't reliably stay inside the narrow tool schema | Medium | Zod-validate every tool call; invalid args become a tool-result error turn, not a crash |
| `resolveRef`'s structural extension doesn't generalize past the one row-header case it's built from | Medium | Scoped deliberately to that one proven pattern; anything else still throws loudly |
| Checkpoint-derivation heuristic (colon-split prefix) misses a PII-bearing heading with no separator | Medium | The safety net (decision 4) checks derived text against every known secret/pii value regardless of derivation path — the actual hard guarantee, not the heuristic itself |
| Live discovery runs cost real API tokens and are somewhat nondeterministic | Medium | All branch/logic coverage lives in the `FakeModel` unit suite; live runs in Phase 7 prove the real integration, not the logic |
| Dead-end snapshot-equality false-positives on incidental noise | Low | target-app is static/deterministic enough; equality ignores `ref`/`ordinal`, compares role/name/text/attrs/children |
| A secret leaks to the model or into evidence | Medium | Redaction at two layers (compact view, evidence writer), both directly unit-tested |
