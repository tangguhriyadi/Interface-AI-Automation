# Plan: `/automation` core — schema, surface adapter, replay executor

**Source**: conversational request (no PRD)
**Selected scope**: `/automation` core only — Zod artifact/app-profile/tenant-overlay schemas, the Playwright surface adapter with a unified structured perception path, and the deterministic replay executor. No LLM, no discovery loop, no escalation mechanism, no CLI — those are later plans.
**Complexity**: Large

## Summary

Build `/automation` as its own npm project (independent of `/target-app`, no workspace) implementing the three pieces CLAUDE.md requires before discovery can exist: (1) Zod schemas for the capability artifact, the app profile, and the tenant overlay; (2) a Playwright-backed surface adapter with **one** perception path — a parsed, structured accessibility-tree snapshot with stable per-frame refs — used by both replay's checkpoint/outcome/recovery matching now and by discovery's ref-to-locator resolution later; (3) a deterministic replay executor that runs a capability artifact against typed inputs and returns the four-way `success | business_outcome | escalated | failed` result, with recovery-rule checking at every transition, app-profile outcome detection, allowlist enforcement, built-in redaction, and structured per-step records from the start. Validated with a hand-written `lookup_member_savings_balance` artifact run against the live target-app: normal success (10001), `member_not_found` (99999), interstitial recovery-then-success (10003), and a beta-tenant re-run proving the overlay mechanism.

## Research findings (verified against real Playwright docs, not assumed)

- `page.accessibility.snapshot()` has been **removed** from current Playwright (API reference page 404s; confirmed via search that it was sunset after a long deprecation). Cannot be used.
- `locator.ariaSnapshot()` / `page.ariaSnapshot()` return a **YAML string**, scoped to whatever locator you call it on — per-frame capture means calling it once per frame. There is no official parsing utility and no built-in concept of a stable ref/id in the raw API (that's a Playwright **MCP** convention, not exposed by the plain `playwright` npm package this project installs).
- The YAML is standard YAML structurally (a sequence whose items are either a plain scalar string, a single-key mapping whose value is a nested sequence, or a single-key mapping whose value is a plain string for special properties like `text:`), with Playwright's own shorthand (`role "name" [attr=value, ...]`, or a bare `role` when there's no accessible name) embedded inside each scalar/key. This means the structural nesting can be parsed with a standard YAML library, and only the per-node shorthand needs a small hand-written extractor — not a fully custom grammar.
- Target-app's balance panel is `<iframe title="Account Balance">`. Playwright's `Frame.name()` reads the `name` attribute, not `title` — frame targeting goes through `page.frameLocator('iframe[title="Account Balance"]')`, not name-matching. (Phase 1 update: the schema itself never stores that selector — it stores a structured `{ by: "title", value: "Account Balance" }`, and only the Phase 2 adapter is responsible for turning that into a `frameLocator` call. See design decision 11.)

Sources: [Snapshot testing | Playwright](https://playwright.dev/docs/aria-snapshots), [deprecate old accessibility API in favor of the new one · Issue #16159 · microsoft/playwright](https://github.com/microsoft/playwright/issues/16159)

## Design decisions

1. **`/automation` uses a flat internal layout**, not a nested source folder. `/automation/package.json` sits at the project root with organized subfolders (`schema/`, `adapter/`, `executor/`, `config/`) directly under `/automation/`, and `/automation/test/` as a sibling — unlike target-app, which nests its code one level down in `target-app/src/`. No functional difference, just a naming choice: this project's own folder name already says what it is, so it doesn't need an inner "source" folder to say it again.
2. **Capability/app-profile/tenant-overlay data files live in repo-root `/capabilities/`**, not inside `/automation/` — matching the stated repo layout exactly. Authored as JSON, loaded and Zod-validated at runtime (`loadCapability`, `loadAppProfile`, `loadTenantOverlay`) — a real proof of "validated at load time, not assumed," and matches how a future `discover` command would emit them.
3. **Login is just the artifact's first few steps**, with `username`/`password` as declared inputs — never literals, never read from target-app's own `.env`. `/automation` gets its own copies of the same test credential values in its own `.env`.
4. **Irreversible steps are a real, typed path that stubs cleanly to `escalated`.** The `safe`/`irreversible` classification exists in the schema now; an irreversible step with no escalation handler wired returns `status: "escalated"` with a reason, never silently proceeds. `lookup_member_savings_balance` has zero irreversible steps, so this path is only exercised by a unit test with a fake artifact.
5. **Integration tests assume target-app is already running** (`TARGET_APP_BASE_URL`, matching the two-terminal workflow in `target-app/README.md`) rather than spawning it as a child process from `/automation`. Fails fast with a clear message if unreachable.
6. **One perception path, not two.** Rather than splitting "raw YAML for discovery" from "targeted queries for replay," the adapter parses each frame's `ariaSnapshot()` YAML into a structured `SnapshotNode` tree (role, accessible name, text, attrs, frame, ordinal) and assigns a **stable per-frame ref** to every node via a deterministic pre-order traversal (stable = reproducible across repeated snapshots of an unchanged page, not a permanent global id). `resolveRef(snapshot, ref)` translates a ref back into a locator via role+name+nth — this is the literal "system builds the locator" mechanism CLAUDE.md's discovery loop describes, built and unit-tested now even though nothing calls it live until the discovery plan exists. Checkpoint verification and app-profile outcome/recovery shape-matching (Phase 3/4) are pure functions that walk this **same** tree — one implementation, not two that could drift. The raw YAML text is retained per frame only as an evidence/debug string, never re-derived differently by a second code path.
7. **Inputs are permissive by construction.** The Zod input schema validates type and presence only — no regex, no length/format refinement on `memberId` or any other declared input. If Zod rejected a malformed-but-well-typed input before the browser ever opened, target-app's own `Invalid Input` and `Member Not Found` pages could never be exercised, and the brief explicitly asks for a replay that hits an error state. Zod (or a thin wrapper around it) throws only for a genuinely missing input or a wrong JS type (e.g. a number where a string input is declared) — everything else is the app's answer to give, observed and reported by the executor, not pre-empted by the schema.
8. **Redaction is built into the input model from this phase, not retrofitted.** Every declared input carries `sensitivity: "secret" | "pii" | "none"`. A small `redact()` helper is threaded through step-record construction and error-message construction starting in Phase 4. Validated with a unit test asserting the literal password value never appears in a `StepRecord` or in a deliberately-failed result's diagnostic fields — the login password is the concrete test case; `memberId` is marked `pii` as the second, distinct case.
9. **The result contract carries `steps: StepRecord[]`** (step id, action, which locator-chain strategy actually matched, outcome, duration, recoveries fired) on every one of the four result variants, present from the first implementation of the executor — not added after the fact once evidence-file work begins in a later plan. `recoveries: string[]` becomes a deduped summary derived from these records rather than a separately-tracked list.
10. **The beta-tenant scenario stays in scope** (kept from the original plan) as the one concrete proof the tenant-overlay mechanism works — the same artifact, unmodified, re-run against `TENANT=beta` and still succeeding despite "Member ID" rendering as "Account Number."
11. **A capability has exactly one navigation entry: `entryPoint`** (a path, resolved against the tenant overlay's `baseUrl` at replay), and no free "navigate to X" step kind exists in `step.ts`. Every other transition happens by acting on the page, so the allowlist's route prefixes bound everywhere a run can ever go — a general navigate step would let an artifact step around that boundary.
12. **Cross-field integrity is enforced at schema load, not discovered at replay.** `CapabilityArtifactSchema.superRefine` checks every step's `fromInput` names a declared input, every read step's `outputName` names a declared output, and every declared output is written by at least one read step — a typo would otherwise silently yield a "successful" replay with a missing output. Symmetrically, `loader.ts` adds `validateBusinessOutcomesAgainstProfile`/`loadCapabilityWithAppProfile`, checking every name in a capability's `businessOutcomes` actually exists in the app profile's `outcomes` — this one can't live inside the capability schema itself since it needs both files.
13. **Waiting is either a per-step timeout or a profile recovery rule — deliberately, never a hardcoded executor constant.** `step.ts`'s `timeoutMs` covers a response that's simply slow with no detectable in-page state (target-app's member `10004` — the delay has no spinner or interim page for a recovery rule to match against, so it's recorded on the step that triggers it). `appProfile.ts`'s `wait` recovery action stays for the *other* case: a genuinely detectable "still loading" page state that `detect` shapes can match, then wait out. The executor (Phase 4) must read one of these two artifact-declared numbers, never bake in a scenario-specific constant of its own.
14. **`frame` is a structured reference, not a CSS selector.** `schema/frame.ts`'s `FrameRefSchema` (`{ by: "title" | "name" | "url", value: string }`) replaces the raw-string frame field everywhere it appeared (step, checkpoint, detector shape). The artifact names a frame the way a human would; only the Phase 2 adapter translates that into whatever the surface needs — a `frameLocator` selector on web, potentially a window/pane lookup on a future desktop adapter. This is the one place the original schema draft was DOM-brittle, and it's fixed before anything is built on top of it.

### Phase 2 — Surface adapter + structured perception (done)
- **Action**: live spike against the running target-app — captured real `ariaSnapshot()` YAML for the login form, search form, member-detail table, and balance-panel row-header table; results and raw captures saved to `evidence/accessibility-snapshot-spike/`. Two of three assumptions held (`<th scope="row">` → `rowheader`; `password` input → `textbox`); one was wrong (layout tables are NOT reclassified — every table reports plain `role="table"`, distinguishable from data tables only by the presence of `rowheader` cells) and one extra surprise turned up (an iframe's `title` attribute does not surface as its accessible name — `getByRole('iframe', {name})` finds nothing; `frameLocator('iframe[title="..."]')` does). - **Validate**: parser tests against the captured real-fixture YAML (copied into `automation/test/fixtures/`) plus synthetic edge cases (no name, nested `text:`, repeated role+name siblings → ordinal assignment, deterministic refs across repeated parses); locator-chain fallback, structural/label resolution, and frame-targeting tests against small local HTML fixtures (`file://`, not target-app); a ref-resolution round-trip test. 11 test files, 99 tests, all passing — the 6 adapter tests launch a real (local-only) Chromium session, ~1.3s.

Result: every signal already matched exactly; no JSON changes were needed. `capabilities/README.md` records the provenance and points to the evidence.

### Phase 4 — Deterministic replay executor (done)
- **Action**: `redact.ts` (`redactForLog`); `replay.ts` — one `checkTransition()` function is the single place detection order lives, run at every transition: (1) `adapter.lastNavigationStatus()` ≥ 500 → hard failure (`http_error`), checked before any content is read; (2) allowlist boundary; (3) session-expiry — matched against the app profile's `sessionExpiry` detector shapes (see the post-Phase-4 fix below — this was originally, incorrectly, inferred from `entryPoint`), guarded by `hasLeftEntryPoint` (set the first time a transition lands off `entryPoint`) so a coincidental revisit before ever leaving can't false-positive; (4) business outcome match against the app profile; (5) recovery match — dismissed and looped back to (1), bounded both per-rule and overall (`recovery_exhausted`), with the dismiss action itself also guarded (`recovery_action_failed`); (6) checkpoint, only on the final transition. A step's own locator-resolution failure routes through the same function before being called a failure, so an outcome/recovery can still explain it.
- Any would-be `failed` result is decided by one `classify()` helper: if the step that just ran is `irreversible`, it's `escalated` instead — never retried.
- **Irreversible steps — resolved via conversation, revising decision 4**: gated by `allowIrreversible` on the `replay()` call (default `false`). Without it: stops before attempting, `escalated`, `StepRecord.irreversibleExecutionAuthorized: false`. With it: executed exactly like a safe step; ambiguity afterward (hard failure or session-expiry) still escalates per the rule above and is never retried; recovery-dismissal (e.g. clicking away an interstitial) is not considered "retrying the step" since it doesn't repeat the step's own action. `StepRecord.irreversibleExecutionAuthorized: true` records that it *was* attempted and under what authorization.
- **Tenant translation, not in the original plan**: `translateLocatorChain()` maps a locator chain's `name`/`text`/`rowHeader` through `TenantOverlay.controlNameOverrides` before the adapter ever sees it. Without this the beta-tenant Phase 5 scenario has no mechanism to actually work — nothing built in Phases 1–3 did this translation.
- **Redaction is real, not incidental**: `StepRecord.attemptedValue` (type/select steps only) is always passed through `redactForLog(value, sensitivity)` before being stored — never the raw value. Diagnostic `expected`/`observed` strings are deliberately structural (status codes, paths, step ids, error classes) and never quote raw page text, since headings/alerts can carry a member's name — nor the raw URL on an allowlist violation, since a path can carry a memberId (`pii`).
- **Allowlist enforcement was in the original plan's Phase 4 scope and got missed on the first pass** — caught only while writing this summary, not by a test. Added `isWithinAllowlist()`, checked every transition (origin + route-prefix match against `appProfile.allowlist`), positioned right after the HTTP-status check and before session-expiry. New error class `allowlist_violation`; two dedicated tests (off-origin, and on-origin-but-off-route).
- Error class taxonomy: `allowlist_violation | http_error | session_expired | locator_not_found | checkpoint_not_met | recovery_exhausted | recovery_action_failed`.
- `SurfaceAdapter` gained `lastNavigationStatus()` (`playwrightAdapter.ts` tracks it via a `response` listener on navigation requests, redirect chains included) — needed for hard-failure detection, not anticipated in Phase 2.
- **Three fixes made after the first Phase 4 pass, before Phase 5:**
  1. **Output sensitivity.** `OutputSpecSchema` gained the same `sensitivity` enum as inputs (renamed `InputSensitivitySchema`/`InputSensitivity` → `SensitivitySchema`/`Sensitivity`, since it's no longer input-specific) — a member name read off the page is exactly as much PII as one typed in. `StepRecord` gained `observedValue` (read steps only), always passed through `redactForLog` per the *output's* sensitivity. The value stays unredacted in a `success` result's `outputs` — that's what the caller asked for — redaction applies everywhere else (logs, step records, error messages), so a later evidence-writing plan can serialize `StepRecord`s directly without re-deriving sensitivity itself.
  2. **Debuggable diagnostics.** `describeCheckpointMiss()` reports what was actually observed instead of a generic "condition not met": for `heading_starts_with`, whether a heading was present at all, and if so that it didn't match (the heading text itself redacted via `redactPageText`, i.e. treated as PII by default — page content, unlike a locator's own rationale, isn't something the executor can vouch for); for `frame_present`, which frame ids *were* seen (structural, not page content, safe unredacted); for `text_contains`, that the expected substring wasn't found anywhere. `adapter/surfaceAdapter.ts` gained `LocatorResolutionError` (thrown by both `playwrightAdapter.ts` and `FakeAdapter`) carrying the per-strategy attempt list (kind, rationale, match count) — safe to surface verbatim since it's artifact metadata, not page content — so a `locator_not_found` result's `observed` now names which strategies were tried and how close each came, instead of a fixed generic string.
  3. **Session-expiry as an app-profile signal, not an entryPoint inference.** The original mechanism ("landed back on `entryPoint`'s path") only worked because this capability's `entryPoint` happens to be `/login`; a capability starting at `/search` would never have detected an expiry redirect. `AppProfileSchema` gained `sessionExpiry: DetectorShape[]` (optional — same shape-matching mechanism as outcomes/recoveries), matched via `matchesAnyShape`. `hasLeftEntryPoint` stays, but now purely as the false-positive guard the earlier design already had, not the detection mechanism itself. Verified live against target-app (not inferred): started it with `EXPIRE_SESSION_AFTER_REQUESTS=1` (env-var override, not a code change) and captured the actual expired-session page — heading identical to the plain login page ("Log In"), distinguished *only* by a `role="alert"` notice ("Your session expired. Please log in again."), saved to `evidence/app-profile-verification/session-expired.aria.yaml`. The real app profile's `sessionExpiry` shape matches this exactly.
- **Validate**: `test/support/fakeAdapter.ts` (queued snapshots, settable navigation status, scriptable action failures, now throwing `LocatorResolutionError`) backs `test/executor/replay.test.ts` — happy path; allowlist violation (off-origin, and on-origin-but-off-route); each detection-order layer in isolation (hard failure, business outcome short-circuiting remaining steps to `"skipped"`, recovery dismiss-and-continue, checkpoint miss with redacted diagnostic detail, a `frame_present` miss listing frames seen, a `locator_not_found` naming strategies tried); the session-expiry false-positive guard (typing before ever leaving `entryPoint`, *and* a coincidental plain revisit to `entryPoint` with no expiry signal present) and the true-positive case (now matched against the real app-profile shape); bounded recovery exhaustion; all four irreversible-step scenarios; a locator failure on a safe step staying a plain `failed`; redaction holding on both a successful run and a failed one; and output redaction specifically (a PII-sensitivity output stays unredacted in `outputs` but redacted in `StepRecord.observedValue`, with `JSON.stringify` on the step records alone asserted not to contain the literal value). 13 test files, 136 tests, all passing, no browser needed for any of Phase 4's own tests.

### Phase 5 — Hand-written artifact + live validation (done)
- **Action**: `capabilities/lookup-member-savings-balance.artifact.json` — 6 steps (type username/password, click Log In, type memberId, click Search, read savings balance via the row-header structural locator inside the `Account Balance` frame, `frame: {by:"title", value:"Account Balance"}`); `successCheckpoint`: `frame_present`. Inputs: `username` `none`, `password` `secret`, `memberId` `pii` — deliberately exercises all three sensitivity levels. Output `savingsBalance`: `pii`. `businessOutcomes`: all three the app profile declares (`member_not_found`, `access_denied`, `invalid_input`), not just the one scenario required — a real capability could hit any of them. One step (`click-log-in`) carries a two-strategy chain (role+name primary, a scoped CSS fallback marked `brittle: true`) as a concrete, schema-valid demonstration of the fallback mechanism against the real app, not just the Phase 2 local-fixture tests. Validated schema+cross-file correctness (`loadCapabilityWithAppProfile`) before writing any test.
- **Live validation found a real gap, not a test-setup artifact**: the allowlist's `originPattern` was hardcoded to the app profile's single default origin, but a tenant can legitimately run on its *own* origin (its own subdomain/port) — discovered only by actually trying to run the beta-tenant scenario against a second target-app instance. Fixed: `replay()` now resolves the allowlist's origin as `options.tenantOverlay?.baseUrl ?? appProfile.allowlist.originPattern` — the tenant's own declared origin takes precedence when a tenant overlay is in play, route prefixes staying app-level either way. This is a safety mechanism working as intended, not something to route around: it refuses to trust an origin nobody declared. Verified the beta scenario **sequentially, at full fidelity** — target-app restarted with `TENANT=beta` at the exact URL `fake-credit-union-console.beta.tenant-overlay.json` declares (not a second port papering over the mismatch) — confirmed passing, then reverted target-app to normal for ongoing use.
- **Validate**: `automation/test/integration/lookupMemberSavingsBalance.test.ts` (requires a live target-app on `TARGET_APP_BASE_URL`), `npm run test:integration` invoking `node --env-file=.env` directly (`NODE_OPTIONS=--env-file` is rejected by Node — the integration tier genuinely needs real credentials from `.env`, unlike the fast unit tier which stays `.env`-free by design): `10001` → `success`, correct `savingsBalance` output (`$1,234.56`), empty `recoveries`, full `steps[]` all `"ok"`; `99999` → `business_outcome: "member_not_found"`; `10003` → `success`, `recoveries: ["maintenance_interstitial"]`; beta tenant + `10001` → `success` despite the renamed label — gated behind `TARGET_APP_BETA_BASE_URL` (skipped, not failed, when unset — deliberately not kept "always on" in `.env`, since a stale value would fail instead of skip against a default-tenant instance). Password confirmed absent from `JSON.stringify(result)` on every scenario. 3 required live scenarios pass; beta scenario proven separately at full fidelity.

### Post-Phase-5 additions, before Phase 6 (done)
- **`memberName` output.** A capability that returns a balance with no way to verify whose balance it is gives the caller nothing to check the reply against — and it makes parameterised replay only visibly real when a *different* memberId also returns a *different* name, not just a different number. `outputs.memberName` (`sensitivity: "pii"`) added ahead of `savingsBalance`; a new `read-member-name` step (structural locator, `rowHeader: "Name"`, same pattern as the balance read) inserted between `click-search` and `read-savings-balance`. Verified live: `10001` → `"Elena Cho"`, `10003` → `"Dana Okafor"` — two different memberIds, two different names, both asserted in `test/integration/lookupMemberSavingsBalance.test.ts` (including the beta-tenant case).
- **Per-step `checkpoint` — a real schema gap, not a workaround.** Before this, only `capability.successCheckpoint` existed, and it's checked exclusively on the last step (`checkCheckpoint: isLastStep`). A mid-flow step that lands on the wrong page would go undetected if that wrong page happened to still satisfy the final checkpoint — e.g. `click-search` landing somewhere that coincidentally has an `Account Balance` frame present. Fixed by adding `checkpoint?: Checkpoint` to `baseStepFields` (`schema/step.ts`) — same `Checkpoint` shape as `successCheckpoint`, evaluated by the same `evaluateCheckpoint`. New error class `step_checkpoint_not_met` (distinct from the final-step `checkpoint_not_met`) added to `executor/replay.ts`'s `ErrorClass` union and evaluated inside `checkTransition`, positioned **after** the recovery loop settles and **after** business-outcome detection — confirmed by inspecting check order (`grep -n` on `replay.ts`: business outcome at line 252, per-step checkpoint at line 310, final checkpoint at line 322) — so a legitimate `member_not_found`/`access_denied`/`invalid_input` landing still short-circuits to `business_outcome` before the new per-step checkpoint could ever misfire on it. Applied to the real artifact: `click-search` now carries `checkpoint: { kind: "heading_starts_with", text: "Member:" }`.
- **Validate**: 2 new schema tests (`test/schema/step.test.ts`: checkpoint accepted; invalid checkpoint kind rejected) and a new `describe` block in `test/executor/replay.test.ts` proving the exact scenario motivating the change — a step landing on a page that would satisfy the *final* `successCheckpoint` but fails its *own* checkpoint is caught immediately (`errorClass: "step_checkpoint_not_met"`, remaining steps `"skipped"`), and a clean pass-through when the step's own checkpoint is satisfied. Fast unit suite: 13 files, 140 tests (up from 136), all passing. Live suite re-run against target-app after both artifact edits: `10001` → success with correct `memberName`+`savingsBalance`, `99999` → `business_outcome: member_not_found` (confirming the checkpoint addition doesn't regress outcome detection live, not just in the fake-adapter test), `10003` → success + recovery + correct `memberName`, all password-redaction checks still passing; beta scenario still skips by default (`TARGET_APP_BETA_BASE_URL` unset).

## Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| Real browser role computation doesn't match assumptions (nested tables, row headers) | Medium | Phase 2's live spike runs first and adjusts code to observed reality — biggest unknown in the plan |
| Parsing Playwright's `ariaSnapshot()` YAML shorthand is more irregular than documented examples suggest | Medium | parser tests run against real captured target-app YAML (not just doc examples) before anything depends on it |
| Recovery loop could infinite-loop on a dismiss that doesn't clear the condition | Low | bounded retry per transition, then `failed` |
| Redaction gap: a secret/pii value leaks through an error path nobody wrote a test for | Medium | explicit redaction tests in both the fake-adapter unit suite and the live integration suite, not just one |
| Scope creep across 4 subsystems (schema, adapter+perception, app profile, executor) in one plan | Medium | phased, stop-after-each per the working-style rule |
